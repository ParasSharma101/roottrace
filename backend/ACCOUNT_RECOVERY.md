# Password recovery and session revocation

Decision: 2026-11-18. Security owns account recovery, session identifiers and revocation. Workspace selection continues to use current membership; mail infrastructure owns encrypted outbound delivery. This increment builds on V8 verified email/invitations and does not deploy a live migration or send external email.

## Rules and API

| Endpoint | Authentication and result |
| --- | --- |
| `POST /api/v1/auth/password/forgot` | Public JSON `email`. Valid input receives the same 202 acknowledgement for known/unknown addresses, suppressed requests, or disabled delivery. No token or eligibility is returned. |
| `POST /api/v1/auth/password/reset` | Public JSON `token`, `password`. One valid emailed proof changes the password; 200 contains status only, never a session. Invalid/expired/used proof returns 400, peer limit 429, disabled delivery 503. |
| `POST /api/v1/auth/logout` | Account session required; 204 revokes the entire current session family, including previously issued workspace selections. |
| `POST /api/v1/auth/logout-all` | Account session required; 204 increments the account's authentication epoch and invalidates every existing account session. |

Forgot-password intake performs no account lookup. It encrypts the normalized email in `password_recovery_requests`, then acknowledges the request. A private worker resolves account eligibility later, so account locks/eligibility do not affect public response timing. Peer-limit suppression is also acknowledged generically. Database outages can return 503 consistently without disclosing account existence. This is not a guarantee of constant network latency.

The worker creates a 32-random-byte reset proof, storing only SHA-256 in `password_resets`, and atomically queues its encrypted SMTP email. Proof lifetime is 30 minutes. Multiple still-valid proofs may coexist: another anonymous request cannot invalidate a link already in the recipient's inbox. One successful reset consumes that proof and revokes every other unused reset and verification link, cancels/scrubs their unsent messages, increments the authentication epoch, changes the BCrypt password, and queues a password-change notification in one transaction. A queue/database failure rolls everything back. Account, reset-proof and login locks serialize password changes and session issuance. Concurrent use of the same proof succeeds once.

Recovery is available for unverified accounts as well: the valid emailed proof confirms ownership of the matching current address while replacing the password and invalidating previous sessions. Proofs cannot verify a changed address. Resetting does not accept invitations, alter membership/roles, or select a workspace. It issues no JWT; use normal password login afterwards. Ingestion keys remain active and require separate workspace-administrator revocation during compromise recovery. A password reset alone is not a complete incident response process.

New signup/reset passwords require at least 15 Unicode code points and no more than 72 UTF-8 bytes, preventing silent BCrypt truncation. No complexity rules or silent trimming. The existing BCrypt algorithm/cost are retained; existing shorter passwords can still log in. This increment does not add a breached-password list, MFA or a new hash algorithm. Frontend validation matches the server, with two password fields on reset. Reset links use a fragment, immediately scrubbed into page memory; only an explicit POST changes a password. No secret is put in browser storage/query parameters or returned by the API. Requests and password DTO string representations are redacted.

## Sessions and V9 rollout

JWT version 3 adds random UUID session identity (`jti`) and the account's `authEpoch`. The database owns `users.auth_epoch` and `revoked_sessions`; every authenticated request checks both current epoch and individual revocation, alongside live membership. No authorization role is trusted from the token. Login/signup create a new session family. Selecting another workspace preserves its session ID, epoch and original expiry; it does not extend lifetime. The configured absolute expiry remains unchanged (24 hours by default). Logout revokes all tokens in that family; logout-all/reset revoke all families through the epoch. There is no device list, refresh token, idle timeout or targeted remote-device API in this increment.

V9 preserves account passwords, verification state, memberships and existing queued emails. It adds the epoch, revocation records, hashed proofs, encrypted request intake and peer counters, and extends outbound mail references/purposes. V1-V8 remain immutable. Version 2 tokens require fresh login. Snapshot/restore and a coordinated backend rollout are required: do not run old and new backends together, since old instances cannot enforce the new revocation contract. Restoring older account/revocation state can restore old session validity; rotate the signing key after a security-sensitive restore. No live data was migrated during implementation.

Revocation applies to subsequent authentication. Requests already authenticated may complete. Workspace switching and new login additionally serialize against recovery/revocation; neither can mint a replacement from an already revoked session. A database failure prevents authentication; do not cache a successful epoch/revocation lookup across requests. Local storage remains the existing bearer-session transport; protection against browser script compromise and cookie-based sessions need a separate decision.

Frontend sign-out waits for server revocation before clearing credentials. On a network failure it retains the session for retry. A 401 on current-session logout means that session is already inactive and allows local cleanup; a 401 on logout-all requires fresh login and does not claim account-wide success. Other tabs discard their mounted workspace views when the stored token changes; proof pages can retain their in-memory link while authentication changes.

## Delivery, limits and operations

Use the SMTP settings in [EMAIL_INVITATIONS.md](EMAIL_INVITATIONS.md). Mail must be enabled with the dedicated encryption key for recovery intake and reset completion. Disabled delivery leaves signup/login/logout available but recovery requests are generically acknowledged without queueing an email. The existing dedicated mail scheduler first processes up to ten recovery requests, then up to ten outbound emails per tick. SMTP calls stay outside transactions.

Intake claims have a five-minute lease, five attempts and 10/20/40/80-second backoff. Processing a claim, creating any proof/email and scrubbing the intake payload commit atomically. Request bodies expire after 30 minutes or exhausted retries and are scrubbed; completed/failed intake metadata is pruned after seven days. Peer counters older than a day and expired individual-session revocations are pruned in bounded batches when recovery delivery runs. With mail disabled that cleanup pauses; retain revoked-session records at least until JWT expiry. Reset/proof/email audit metadata still needs the broader retention policy. There is no intake/mail redrive API: fix configuration and request another link. Monitor request/mail pending age and failures through trusted operations without decrypting bodies. SENT means SMTP submission, not inbox delivery.

Distributed database limits apply across backend instances:

- `roottrace.recovery.requests-per-account-hour`: default 5 issued reset emails per rolling hour. A 60-second per-account cooldown also applies under the account lock. Suppression does not change existing links, passwords or sessions.
- `roottrace.recovery.requests-per-peer-window`: default 20 total forgot/reset attempts per fixed 15-minute window. Counters include unknown accounts. Only the direct socket peer is used; forwarded headers are ignored. Counters store a purpose-separated HMAC of the peer, not a plaintext IP. Signing-key rotation resets counter identity.

Configure deployment-level client limits before public exposure. Through the Next.js proxy, multiple users share the frontend's direct peer; the backend budget therefore becomes shared. Review that budget and enforce per-client limits at trusted HTTPS ingress. This implementation intentionally does not accept a user-controlled forwarded IP as trusted identity. Broader login/signup throttling, ingress/DDoS controls, provider quotas, external alerts and compromised-account response remain pending. No full standards-compliance claim is made.

## Validation and references

Integration tests use disposable PostgreSQL/Redis/Kafka and loopback SMTP. They cover successful reset and notification, hash/encryption, old/new password login, all-session revocation, workspace-family logout and expiry preservation, fresh login after logout-all, malformed/expired/stale/wrong-purpose proof, concurrent single-use consumption, quota/cooldown/forwarded-header denial, and rollback if notification enqueue fails. A locked-account test proves public acknowledgement occurs before eligibility lookup. V8-to-V9 upgrade coverage preserves account/mail state. Unit tests reject old/incomplete signed tokens and check Unicode/byte boundaries. Frontend checks cover confirmed/failed/expired sign-out and reset proof storage/transport. A random-port HTTP smoke check exercises signup, reset request, SMTP proof, reset, fresh login, logout-all and subsequent rejection over TCP.

The design was checked against [OWASP password recovery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [session management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), and [password strength guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html). These informed generic asynchronous acknowledgement, bounded single-use proof, notifications, fresh login and server-side revocation. Production SMTP/DNS delivery and browser interaction still need deployment/manual verification.
